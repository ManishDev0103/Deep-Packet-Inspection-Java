## Visual Hierarchy

### React primary screen
- Primary anchor: the large “See what's moving through your network.” heading and mint accent eyebrow establish the page-level entry point.
- Action anchor: the Capture File (01) and Blocking Rules (02) panels sit below the heading as the two equal-width setup cards; the mint “Inspect traffic” action is the sole primary workflow CTA.
- Report anchor: after successful processing, the “Traffic report” header is the next dominant heading, followed by the four metric cards, then filtering/application detail cards.
- Secondary hierarchy: keep numbered section markers, card labels, and metadata in muted smaller type; reserve mint for status, focus, brand, and primary action emphasis rather than applying it to every label.
- Do not add a competing hero or full-page redesign. Preserve the existing dark charcoal/mint card structure and compact report density.

### Legacy report and rules surfaces
- Primary anchor: each legacy page title in the header establishes route identity, while the page `<h2>` headings (“DPI Rule Overview,” “Recent Inspected Flows,” “Active Rule Stats,” “Add Blocking Rule,” “Delete Blocking Rule”) establish each content section.
- Report hierarchy: rule-stat cards are the first summary layer; “Recent Inspected Flows” and its table are the primary data surface. Forwarded/blocked action text remains a semantic state, not a decorative accent.
- Rules hierarchy: active-rule stats provide overview context above two distinct action cards. “Add Rule” is the normal slate/blue primary action; “Delete Rule” remains isolated as destructive red treatment.
- Secondary hierarchy: labels, table headers, helper text, alerts, and footer remain smaller/slate-toned. Blue reserved for navigation, links, and primary actions; red reserved for errors and deletion only.
- Preserve the existing slate/blue card and table patterns; repair labels, feedback, overflow, and navigation without changing page architecture or packet data meaning.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | React: “Inspect traffic”; legacy add rule: “Add Rule” |
| Empty state heading | React: “No classified application flows.” |
| Empty state body | “Process a PCAP file and the detected application flows will appear here.” |
| Legacy report empty state | “No flow records found. Process a PCAP file to view flows.” |
| Error state | React: “Please choose a PCAP file to inspect.” before processing; processing/API failures retain the returned problem plus actionable next step. Legacy: “Failed to add rule / Failed to delete rule” followed by the concrete validation or service problem. |
| Success state | React: “Analysis complete — {count} packets inspected.” Legacy: “Rule added: {type} = {value}” or “Rule deleted: {type} = {value}”. |
| Destructive confirmation | Before a blocking-rule deletion POST, show an explicit in-flow confirmation naming the exact stored rule value: “Delete rule `...`?” The keep action is `Keep Blocking Rule`; the destructive action is `Delete Rule`. Do not add phone or email actions. |

Form guidance:
- Remove placeholder-only and hint-placeholder examples for all forms. WEB-04 requires persistent visible labels and adjacent helper text.
- Every file/input field has a visible label. Adjacent helper text states the accepted action or format.
- Add Rule guidance must explain the value format and which exact value will be stored.
- Delete Rule guidance must explain that the exact stored value is required; the named confirmation is the final guard.
- React rule fields keep visible labels and adjacent helper text. Do not place hints in placeholder attributes.
